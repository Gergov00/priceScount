## Цель и критерии успеха

Пользователь поручил исправить баги из `PROJECT_REVIEW.md`, найти подходящие скиллы, использовать superpowers для планирования и запускать субагентов на `gpt-6-luna` с `reasoning_effort=low`. Область — все 15 отдельных проблем S1–S8 и F4–F10; F1–F3 совпадают с S2/S3/S1. Дополнительно исправляются связанные ошибки документации и добавляются проверки в CI.

Успех: подписки и события не расходятся при временных сбоях БД/брокера; диалог сохраняет порядок; force не включает периодическое отслеживание; сообщения не удаляются при временной ошибке Telegram; секреты отсутствуют в логах. Повторная обработка задачи не дублирует историю и переход алерта. Все регрессионные тесты, race, build и vet проходят. Реальные интеграционные проверки выполняются на отдельной тестовой инфраструктуре, если она доступна; отсутствие инфраструктуры отражается в результате, без заявления об их успешном прохождении.

## Выбор подхода

1. Только локальные retry и перестановка операций: небольшой diff, но падение между записью БД и Publish по-прежнему теряет событие. Не закрывает S2/S6/F4/F8/F9 полностью.
2. **Рекомендуется: PostgreSQL outbox и версии желаемого состояния.** Сохраняет пять сервисов и существующий стек. Изменения БД и факт постановки работы атомарны; доставка повторяется независимо от HTTP-запроса.
3. Перенос всей координации в один процесс/единый worker: существенно меняет архитектуру, не требуется для текущего исправления.

Выбран второй подход. Новые внешние сервисы не вводятся. Публичные REST-формы остаются совместимыми; успешный commit означает принятие операции на надёжную обработку, а не факт доставки в Telegram.

## Глобальные ограничения

- Go 1.26, PostgreSQL 16, RabbitMQ и существующие библиотеки; дополнительные production-зависимости без необходимости не вводить.
- Сохранить существующие пользовательские данные. Миграции добавляют поля/таблицы и backfill; никакого `down -v`.
- Интерфейсы определяет потребитель, wiring выполняется через fx; соблюдать `CLAUDE.md`.
- Ни один сетевой вызов не выполняется внутри PostgreSQL-транзакции.
- Субагенты: только `gpt-6-luna`, `reasoning_effort=low`; не повышать модель без нового указания пользователя.
- Не отправлять реальные сообщения пользователям Telegram и не использовать production-данные в тестах.
- По последнему указанию пользователя сначала исправляются баги, затем добавляются недостающие тесты. Уже существующие регрессионные проверки используются для подтверждения результата; длительные и инфраструктурные тесты имеют build tag `integration`.
- Не обещать exactly-once Telegram: возможен дубль после успешного send и падения до Ack. Цель — отсутствие тихой потери и идемпотентность до внешней доставки.

## 1. Надёжные события и состояние мониторинга

Gateway и Scheduler получают собственные outbox-таблицы: UUID события, уникальный ключ события, очередь, JSONB payload, created_at, available_at, attempts, lease_token, locked_until, published_at. Частичный индекс ограничен непубликованными событиями. Общий пакет доставщика содержит только цикл claim → Publish → mark/retry; доступ к таблицам реализуется в store каждого сервиса через интерфейс потребителя.

Воркер выбирает небольшую порцию через `FOR UPDATE SKIP LOCKED`, выставляет ограниченный lease и завершает транзакцию. Публикует вне транзакции. Отмечает отправку только после подтверждения RabbitMQ. Обновление завершения/повтора проверяет lease_token, чтобы старый воркер не подтвердил работу нового владельца. При падении lease истекает, событие доступно повторно. Backoff ограничен сверху; временная ошибка не удаляет событие. Постоянно ошибочные payload сохраняются с явной ошибкой и возможностью повторного запуска, а не исчезают.

Broker Publish включает publisher confirms, mandatory routing и обработку returns, reconnect и context deadline. Для однозначного сопоставления confirm/return допускается один in-flight Publish на отдельном publisher channel; consumer channels отделены. Не держать блокировку общего соединения во время внешнего ожидания. Persistent messages и durable queues остаются обязательными.

Для каждого продукта Gateway хранит `monitor_version BIGINT` и вычисляет desired_active как наличие хотя бы одной active/non-paused подписки. Create/pause/resume/delete сериализуются блокировкой строки продукта: в одной транзакции меняют подписку, вычисляют состояние, увеличивают версию при значимом изменении и создают snapshot `set_state` в outbox. Snapshot содержит ProductID, URL, Platform, Version, Active и интервал проверки.

Scheduler хранит последнюю версию в scheduled_urls и применяет только более новую. Не удаляет строку состояния при выключении: inactive-строка сохраняет версию, иначе поздняя старая команда могла бы воскресить товар. Периодический tick в одной транзакции сохраняет scraper task в scheduler outbox и переносит next_check_at. Поэтому ошибка RabbitMQ не отменяет уже сохранённую работу.

Delete идемпотентен: повтор владельца уже удалённой подписки возвращает 204; чужой/несуществующий ID — 404. Outbox-запись не зависит от повторного HTTP-запроса.

Миграция не удаляет старые таблицы. Для старых команд без версии описывается контролируемый переход: остановить старых производителей/потребителей, обработать старые команды до включения versioned protocol, выполнить миграцию и reconciliation, затем запустить новую версию. Не обещать безопасный rolling deploy смешанных команд без версии и с версией. Reconciliation включает inactive-продукты, повторяется после ошибок и не служит заменой outbox.

## 2. Результаты, пороги и ручная проверка

Gateway обрабатывает PriceResult одной транзакцией: идемпотентно регистрирует TaskID, сохраняет history, сериализует переходы состояния подписок и создаёт NotifyTask в outbox. Повтор TaskID не меняет state, не создаёт новую history и не публикует новый алерт. Для существующей history добавить nullable task_id с частичным уникальным индексом, сохранив старые строки; отдельно хранить обработанные TaskID, если это нужно для результатов без history.

При переходе зоны увеличивается alert_version; ключ уведомления стабилен по subscription ID и версии перехода. DB ошибка вызывает Nack/requeue результата. Ack — только после commit. Конкурентные результаты одного продукта обрабатываются в согласованном порядке блокировкой продукта/подписок; результат старше последнего обработанного времени не должен откатывать актуальную зону. Одинаковое время разных результатов допускается, но не создаёт одинаковый переход дважды.

При повторном добавлении подписки старое alert_state сбрасывается, если изменились пороги или восстановлена удалённая подписка. Идентичный retry Create не сбрасывает state и не создаёт повторный алерт.

Force получает стабильный TaskID при сохранении команды Gateway и идентификатор инициатора. Scheduler сохраняет одноразовый scraper task идемпотентно по этому ID. Force **не изменяет active и next_check_at** периодического расписания. Gateway отправляет статус инициатору независимо от paused-фильтра периодических подписок. Авторизация проверяется при создании запроса; для результата сохраняется контекст запроса. Не рассылать статус другим пользователям. Неудачный fetch создаёт понятный ответ об ошибке инициатору вместо молчания.

## 3. Telegram и lifecycle

Sender принимает `context.Context`. HTTP-клиент внедрён, имеет timeout; запросы используют `NewRequestWithContext`. Retry ожидания отменяемы. Временные ошибки — сеть, 429 и 5xx — не подтверждают недоставленное сообщение; учитывается retry_after. Постоянные ошибки вроде blocked chat/invalid payload направляются в DLQ с безопасной диагностикой. После исчерпания локальных попыток временная ошибка возвращается consumer для повторной доставки с задержкой, а не Ack и не бесконтрольного горячего цикла.

Ошибки транспорта санитизируются до логирования: полный URL с token не попадает в slog. Тест использует fake token и fake transport. Проверяются и Notifier, и Bot. Остановка прекращает текущий запрос и retry, ждёт goroutine до закрытия зависимостей.

WB FetchProduct сохраняет lifecycle allocator, но браузерный context отменяется вместе с входящим ctx. Уже отменённый ctx не запускает fetch; лимит 40 секунд остаётся. Отмена consumer не ждёт полного timeout браузера.

RabbitMQ получает named volume `/var/lib/rabbitmq` и стабильный hostname. Тест восстановления пересоздаёт только отдельный тестовый брокер, не рабочие контейнеры.

## 4. Диалог и список бота

Обработка updates сохраняет порядок для одного chat_id, допускает параллельность разных чатов и ограничивает число одновременно работающих обработчиков. Read/write Session не раскрывают общий изменяемый указатель. Lookup выполняется асинхронно, но его завершение проходит через атомарный переход с проверкой ID/версии: /cancel и новый lookup не могут быть перезаписаны поздним ответом. Очереди/worker state освобождаются после простаивания и остановки.

`/mylist` показывает страницы с кнопками вперед/назад. Размер страницы определяется и числом товаров, и лимитом текста Telegram; очень длинное имя сокращается. На странице только кнопки её товаров. Смена страницы, редактирование, pause/delete корректно обновляют текущую страницу, включая удаление последнего элемента. Ошибки Telegram Send/Request обрабатываются, не теряются молча.

Задачи: (1) broker/outbox primitive и тесты; (2) Gateway транзакции/версии/идемпотентные результаты; (3) Scheduler outbox/versioning/force; (4) Notifier/context/retry/security; (5) Bot concurrency/pagination и WB cancellation; (6) миграции, deployment, документация, CI и общий review.
