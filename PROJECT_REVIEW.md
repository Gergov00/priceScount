## Standards: правила проекта и надёжность

### S1 · P1 · Сессии Telegram-бота имеют data race

[state.go:38](D:/priceScount/services/bot/internal/state/state.go:38), [bot.go:79](D:/priceScount/services/bot/internal/bot/bot.go:79), [search.go:90](D:/priceScount/services/bot/internal/bot/search.go:90).

`Store.Get` возвращает оригинальный указатель `*Session` после снятия mutex. Каждый update обрабатывается отдельной горутиной, а обработчики меняют `Step` и `MinPrice` вне блокировки. Mutex защищает map, но не поля объектов. Два быстрых сообщения одного чата могут одновременно стать «минимумом», прочитать несогласованное состояние или перезаписать отмену действия.

Нарушено требование `CLAUDE.md:80` защищать разделяемые данные. **Подтверждено `go test -race` на копии исходного пакета.** Исправление: последовательная обработка по chat_id, атомарные переходы состояния и контроль версии lookup. Возвращать копию Session полезно, но этого недостаточно для сохранения порядка диалога.

### S2 · P1 · Gateway навсегда подавляет алерт, который не удалось поставить в очередь

[consumer.go:141](D:/priceScount/services/gateway/internal/consumer/consumer.go:141), [consumer.go:177](D:/priceScount/services/gateway/internal/consumer/consumer.go:177).

Сначала записывается `alert_state`, затем `notify` публикует сообщение. Ошибка Publish только логируется, а `price.results` получает Ack. Следующая цена в той же зоне сравнивается с уже сохранённым состоянием и не вызывает повторной попытки. Ошибка `SetAlertState` также приводит к пропуску подписки с последующим Ack всего результата.

Нарушено правило `CLAUDE.md:603`: nack+requeue при временной ошибке. **Воспроизведение:** цена 200 при максимуме 100; Publish возвращает ошибку; результат подтверждён, state=`up`; повторная цена 200 больше не вызывает Publish. Исправление: транзакционный outbox для изменения state и создания уведомления, надёжный publisher и идемпотентная доставка. Простая перестановка Publish и UPDATE оставляет окно дублирования.

### S3 · P1 · Notifier подтверждает недоставленное уведомление

[consumer.go:64](D:/priceScount/services/notifier/internal/consumer/consumer.go:64), [consumer.go:80](D:/priceScount/services/notifier/internal/consumer/consumer.go:80).

`Send` после четырёх попыток может вернуть временную сетевую ошибку, 429 или 5xx. `sendTelegram` её только логирует; `handle` безусловно вызывает Ack. Временная недоступность Telegram дольше окна retry удаляет сообщение окончательно.

Нарушено правило `CLAUDE.md:603`. **Подтверждено fake Sender/Acknowledger:** Sender вернул временную ошибку, Acknowledger получил Ack. Исправление: вернуть ошибку наверх, разделить постоянные и временные ошибки, использовать отложенные повторные попытки с ограничением и DLQ; учитывать `retry_after` для 429.

### S4 · P1 · Зависший запрос Telegram блокирует весь Notifier

[alert.go:60](D:/priceScount/services/notifier/internal/alert/alert.go:60).

`http.Post` использует default client без общего таймаута. Метод Send не принимает ctx, retry использует `time.Sleep`. Единственный последовательный consumer может бесконечно ждать ответа одного запроса; новые уведомления остаются в очереди. Отмена сервисного контекста не прерывает эту операцию.

Нарушены требования `CLAUDE.md:71` и `:276` о контексте для I/O. Исправление: внедрённый HTTP-клиент с таймаутом, `NewRequestWithContext`, контекст в Sender и отменяемые интервалы retry.

### S5 · P2 · Extractor игнорирует контекст вызывающего кода

[wb.go:43](D:/priceScount/shared/pkg/marketplace/wb.go:43).

FetchProduct принимает ctx, но создаёт браузерный контекст от `allocCtx`, а timeout — от него же. Уже отменённый входящий ctx не предотвращает fetch, текущая операция не прекращается по отмене consumer. Собственный timeout в 40 секунд ограничивает длительность, но не исправляет отмену.

Нарушено `CLAUDE.md:276`: функция обязана проверять ctx в долгих операциях. Исправление: связать отмену browser context с входящим ctx, сохранив lifecycle allocator, и дождаться остановки работы перед закрытием зависимостей.

### S6 · P2 · Неудачная публикация Scheduler пропускает очередную проверку

[store.go:81](D:/priceScount/services/scheduler/internal/store/store.go:81), [scheduler.go:76](D:/priceScount/services/scheduler/internal/scheduler/scheduler.go:76).

`DueURLs` переносит `next_check_at` на час вперёд до публикации задачи. Если Publish не удался, `dispatch` только делает continue. На следующем минутном тике URL уже не due; кратковременный сбой приводит к отсутствию проверки до следующего интервала. То же окно существует при падении процесса после UPDATE.

Это дефект надёжности, а не замечание стиля. Исправление: сохраняемый outbox либо модель claim/lease с повторной доставкой. Простое освобождение всех блокировок до Publish не должно вернуть дубли между репликами.

### S7 · P1 · Очереди RabbitMQ не сохраняются между down/up

[docker-compose.yaml:2](D:/priceScount/docker-compose.yaml:2).

Для RabbitMQ не задан сохраняемый named volume/bind mount и стабильная идентичность узла. После штатного `docker compose down` и следующего `up` накопленные задачи, результаты и уведомления не восстанавливаются автоматически, тогда как PostgreSQL остаётся. Durable queues и persistent messages не заменяют сохранение данных брокера.

Это дефект эксплуатации. Анонимные тома Docker не удаляет по умолчанию, но последующий `up` не подключает их автоматически — [документация Docker](https://docs.docker.com/reference/cli/docker/compose/down/). Исправление: named volume для `/var/lib/rabbitmq`, стабильный hostname/node name и проверка восстановления после пересоздания контейнера.

### S8 · P2 · Сетевая ошибка Telegram раскрывает bot token в логах

[alert.go:59](D:/priceScount/services/notifier/internal/alert/alert.go:59), [alert.go:62](D:/priceScount/services/notifier/internal/alert/alert.go:62), [consumer.go:81](D:/priceScount/services/notifier/internal/consumer/consumer.go:81).

Токен включён в URL запроса. Ошибка HTTP-клиента содержит URL, возвращается без очистки и логируется в retry и consumer. DNS/transport failure может раскрыть токен всем, у кого есть доступ к логам или их внешнему сборщику.

**Подтверждено без сети и настоящих секретов:** fake transport вернул DNS-ошибку, текст ошибки содержал `FAKE_REVIEW_TOKEN`. Исправление: санитизировать URL/ошибки до логирования, хранить безопасную категорию и причину ошибки. Отдельно проверить аналогичные ошибки Telegram-клиента Bot; в текущем review именно Notifier доказан воспроизведением.

Эвристические code smells не выделены в блокирующие замечания. Также есть отступления от стандартов: глобальный slog вместо внедрения через fx и игнорирование ошибок части `b.api.Send/Request`. Они требуют приведения к правилам, но отдельные номера им не присвоены; конкретный пользовательский эффект одного из них описан в F10.

### F4 · P1 · Pause одного пользователя может остановить мониторинг другого

[handler.go:301](D:/priceScount/services/gateway/internal/handler/handler.go:301), [handler.go:336](D:/priceScount/services/gateway/internal/handler/handler.go:336).

Требование `CLAUDE.md:435`: pause/delete публикуются «только когда у продукта не осталось других активных непаузнутых подписок».

Проверка количества подписок и отправка команды не атомарны относительно add/resume. Сценарий: A ставит последнюю подписку на паузу, получает Watching=0; B подписывается на тот же URL и публикует add; A публикует pause последним. В БД B активен, Scheduler остановлен. Возможен и аналогичный delete после add.

Исправление: атомарно сохранять желаемое состояние продукта и версионированное событие, Scheduler должен отвергать устаревшие версии. Одного mutex в Gateway недостаточно при нескольких репликах.

### F5 · P2 · Принудительная проверка paused-подписки не возвращает цену

[mylist.go:83](D:/priceScount/services/bot/internal/bot/mylist.go:83), [store.go:421](D:/priceScount/services/gateway/internal/store/store.go:421), [consumer.go:125](D:/priceScount/services/gateway/internal/consumer/consumer.go:125).

Требование `README.md:89`: «Проверить — сразу присылает текущую цену»; `CLAUDE.md:431`: статус получает инициатор.

Кнопка доступна на paused-подписке и API принимает запрос, но результат Force отправляется только по списку ProductSubscriptions, который исключает paused. Инициатор видит сообщение «Результат придёт», но результата не получает даже при успешном fetch.

Исправление: отдельно разрешать инициатора разовой проверки независимо от фильтра периодических алертов; проверить право доступа и поведение при удалении подписки во время fetch.

### F6 · P2 · Разовая проверка возобновляет периодический скрапинг paused-товара

[store.go:65](D:/priceScount/services/scheduler/internal/store/store.go:65).

Требование `CLAUDE.md:447`: «pause → UPDATE active=false».

`AdvanceNextCheck`, вызываемый после Force, ставит `active=true`. Пауза последней подписки → ручная проверка → Scheduler продолжает ежечасно скрапить товар, хотя все подписки paused. Это самостоятельный эффект помимо отсутствия ответа F5.

Исправление: Force не должен менять active; возобновление расписания должно происходить только при add/resume и с учётом текущего желаемого состояния.

### F7 · P2 · Повторная подписка сохраняет старое состояние алерта

[store.go:197](D:/priceScount/services/gateway/internal/store/store.go:197).

Требование `README.md:3`: уведомлять о выходе за заданные пользователем границы.

ON CONFLICT обновляет пороги и восстанавливает подписку, но не очищает alert_state. Получить `up`, удалить товар, добавить заново с другим максимумом ниже текущей цены: состояние снова вычислится `up`, и алерт новой подписки будет подавлен. Edit очищает state, повторное Create — нет.

Исправление: сбрасывать или пересчитывать состояние при изменении порогов/восстановлении; сохранить идемпотентность повторной HTTP-попытки, чтобы одинаковый retry не создавал лишних алертов.

### F8 · P2 · Дедупликация алертов не выдерживает две реплики Gateway

[consumer.go:137](D:/priceScount/services/gateway/internal/consumer/consumer.go:137), [store.go:443](D:/priceScount/services/gateway/internal/store/store.go:443).

Требование `CLAUDE.md:434`: «повторный скрейп с ценой в той же зоне не шлёт новый алерт».

Два consumer могут прочитать одинаковый старый alert_state, затем каждый безусловно выполнить UPDATE и Publish. Две задачи на один товар возможны при одновременной force и периодике, а также повторной доставке. Обе реплики отправят одинаковый алерт.

Исправление: атомарный переход состояния с проверкой ожидаемой версии/блокировкой и outbox, уникальный ключ для события уведомления. Отдельно использовать TaskID для идемпотентного сохранения результата: сейчас повторная доставка также добавляет дубли в price_history.

### F9 · P1 · Неудачный DELETE нельзя восстановить повторной попыткой

[handler.go:375](D:/priceScount/services/gateway/internal/handler/handler.go:375), [handler.go:381](D:/priceScount/services/gateway/internal/handler/handler.go:381), [handler.go:412](D:/priceScount/services/gateway/internal/handler/handler.go:412).

Требование `CLAUDE.md:429`: soft delete и публикация track.requests{delete}.

Gateway сначала выставляет active=false, затем Publish может вернуть ошибку и HTTP 500. Повторный DELETE вызывает GetSubscription, который выбирает только active=true, и получает 404 до новой публикации. Scheduler продолжает проверять удалённый товар. Startup resync публикует только add для активных продуктов и не удаляет такие остатки.

**Подтверждено тестом handler на копии:** последовательность HTTP `[500, 404]`, Publish вызван только один раз. Исправление: транзакционный outbox и идемпотентный DELETE, который учитывает уже удалённую запись и незавершённое событие.

### F10 · P2 · Большой список товаров делает /mylist недоступным

[mylist.go:26](D:/priceScount/services/bot/internal/bot/mylist.go:26), [mylist.go:53](D:/priceScount/services/bot/internal/bot/mylist.go:53).

Требование `README.md:84`: доступный список товаров с кнопками управления.

Все подписки собираются в одно сообщение, имена и URL включаются без ограничения общего размера, пагинации нет. Когда текст превышает лимит sendMessage, Telegram отвергает его, а ошибка Send игнорируется. Пользователь теряет список и кнопки паузы/удаления через этот интерфейс. Лимит текста — 4096 символов, [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

Исправление: пагинация с ограничением размера по фактическому тексту, обработка Send/Request ошибок. Ограничение только числа товаров без учёта длины имён недостаточно.

## Дополнительные пробелы

В проекте нет тестов и CI-конфигурации. Необходимы интеграционные сценарии жизненного цикла подписки и повторной доставки, race-тесты диалога и SQL-конкурентности. `go test ./...` из корня, указанный в документации, не охватывает этот workspace: нужны явные пути модулей.

README отстаёт от реализации: указан Go 1.22+, но go.mod/go.work требуют 1.26; упоминается отсутствующий `migrations/scheduler.sql`; учётные данные RabbitMQ указаны как guest/guest вместо Compose defaults pricescount; обязательный INTERNAL_TOKEN не описан в таблице конфигурации. Для миграции alert_state уже есть безопасный повторный запуск init.sql, тогда как README предлагает удаление томов. Документацию следует обновить, чтобы избежать потери пользовательских данных.

Startup resync только добавляет активные продукты, проглатывает ошибки чтения/публикации и не повторяется. Его нельзя считать механизмом полноценного согласования состояния после сбоев pause/delete. Нужен периодический reconciler либо гарантированная доставка версионированных событий.

В shared broker нет publisher confirms и проверки unroutable сообщений. Успех Publish не доказывает принятия брокером; persistent messages без confirms не закрывают окно потери при аварии. Это усиливает S2/S6 и должно учитываться при исправлении доставки; см. [RabbitMQ publisher confirms](https://www.rabbitmq.com/docs/confirms). Текущее строковое распознавание WB нормализует URL к фиксированному хосту, поэтому самостоятельная SSRF-уязвимость через переданную ссылку в этом review не заявляется.
